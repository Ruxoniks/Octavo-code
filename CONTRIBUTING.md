# Как участвовать

Самый полезный вклад — новое задание. Для него не нужно разбираться в коде движка: задание это папка с файлами.

## Новое задание за пять шагов

1. Скопируйте `docs/task-template` в `content/tasks/<номер>-<id>/`. Номер задаёт только порядок папок на диске, реальный порядок берётся из `order` в манифесте.
2. Заполните `manifest.json`: `id`, `chapter`, `order`, `type`, заголовок, краткое описание, сложность, время, подсказки.
3. Напишите `brief.ru.md` — текст задания репликами (см. ниже).
4. Положите стартовые файлы в `files/start/` и эталонное решение в `files/solution/`.
5. Опишите проверки в `check.js`.

Запустите `npm test` — тесты сами проверят, что эталон проходит проверки, стартовые файлы их не проходят, манифест корректен, а бриф разложен на реплики известных голосов.

## Бриф — это диалог

Текст задания подаётся репликами: игра показывает по одной, а не стену на пол-экрана. Формат:

```markdown
[КУРСОР]
Мне нужно наверх — там кнопка, которую очень хочется нажать. Лесенку строишь ты.

---

[ЛОГИКА]
Ступенька — это `<div>` с двумя классами...
```

Разделитель `---` режет текст на реплики, строка `[ИМЯ]` задаёт голос (без неё голос наследуется от предыдущей реплики). Голоса — роли, а не персонажи:

| Голос | Когда говорит |
|---|---|
| `КУРСОР` | ведёт задание, подталкивает, шутит |
| `ЛОГИКА` | объясняет механику и требования |
| `ПАМЯТЬ` | напоминает пройденное, предупреждает о граблях |
| `ТЕРМИНАЛ` | всё, что про консоль и команды |
| `ЗАКАЗЧИК` | приносит требования и правки |

Новый голос добавляется в `src/ui/voices.ts` — тест на неизвестное имя падает специально, чтобы список не расползался.

Держите реплику короткой: одна мысль, три-пять строк. Если получается больше — это две реплики.

## Требования к качеству

**Сообщение об ошибке — часть задания.** Проверка не должна говорить «неверно». Она должна объяснять, что именно не так и куда смотреть:

```js
// плохо
t.assert(steps.length === 5, 'Неправильное количество ступенек');

// хорошо
t.assert(steps.length === 5, 'Нашёл ступенек: ' + steps.length + ', а нужно ровно 5. Проверь, у всех ли <div> есть класс step.');
```

**Задание не должно решаться само.** Стартовые файлы обязаны проваливать хотя бы одну проверку — иначе тесты упадут.

**Проверяйте то, что видно в DOM.** Браузер чинит часть ошибок разметки на лету: например, `</h1>` спокойно закрывает открытый `<h2>`, и в дереве не остаётся следа. Если баг не виден в DOM — его нельзя проверить, нужен другой баг.

**Одно задание — одна новая идея.** Если в брифе приходится объяснять три незнакомые вещи, это три задания.

**Подсказки идут по нарастающей.** Первая — намёк, вторая — конкретное направление, третья — почти готовый код. Не наоборот.

**Никаких внешних ресурсов внутри заданий.** Они работают офлайн: без CDN, шрифтов и картинок из интернета.

**Файлы задания открыты для правки.** Замок (`editor.readonly`) ставится только там, где файл генерирует движок (сборка блоками, снимок терминала) или где чтение — сам смысл задания. Готовый CSS в задании по HTML замка не требует: пусть человек крутит цвета, «Начать заново» вернёт исходный вариант.

## Как писать проверки

`check.js` исполняется внутри песочницы. Доступен объект `t`:

| Функция | Что делает |
|---|---|
| `t.$(sel)` / `t.$$(sel)` | найти элемент / все элементы |
| `t.text(sel)` | текст элемента, пробелы нормализованы |
| `t.attr(sel, name)` | значение атрибута |
| `t.count(sel)` | количество элементов |
| `t.style(sel, prop)` | вычисленный стиль |
| `t.expectStyle(sel, prop, matcher, msg)` | проверка стиля, которая честно пропускается там, где стили не вычисляются |
| `t.parseColor(value)` | `#5f3f54` или `rgb(...)` → `[r, g, b]` |
| `t.rect(el)` | геометрия элемента |
| `t.mascot.canClimb(opts)` | может ли курсор подняться по ступенькам |
| `t.mascot.steps(sel)` | ступеньки, отсортированные снизу вверх |
| `t.assert(cond, msg)` / `t.fail(msg)` | провал проверки с сообщением |
| `t.skip(msg)` | проверка неприменима в этой среде |

Проверку, которой нужен настоящий движок браузера (геометрия, вычисленные стили), объявляйте через `check.browser(...)` — в тестах она пропускается, в игре работает.

Возвращённая из проверки строка становится сообщением об успехе — это хорошее место, чтобы показать результат: «Ступенек: 5», «Курсор добрался до верха».

## Типы заданий

- `code` — редактор и превью. Нужны `editor.files` и файлы в `files/`.
- `dnd` — сборка из блоков. Нужен блок `dnd` с `pool` и `correct`, а в стартовом `index.html` — плейсхолдер `<!-- BLOCKS -->`.
- `read` — чтение кода. Нужен блок `read` с файлом и вопросами; `check.js` можно оставить пустым.
- `ai` — работа с нейросетью. Нужен блок `ai` с целью, списком файлов и вопросами на разбор.
- `terminal` — симулятор консоли. Нужен блок `terminal`.

### Задания с терминалом

Блок `terminal` в манифесте описывает стартовое состояние:

```json
"terminal": {
  "home": "/home/user",
  "cwd": "/home/user/site",
  "files": { "/home/user/site": { "type": "dir" } },
  "git": { "initialized": true, "commits": [{ "message": "Первая версия", "files": ["index.html"] }] },
  "paste": [
    { "command": "node -v", "label": "Что ответила твоя консоль на", "pattern": "^v?[0-9]+[.][0-9]+[.][0-9]+", "hint": "…" }
  ]
}
```

Раннер после каждой команды собирает страницу-снимок и кладёт состояние сессии в `<script id="session" type="application/json">`. Проверки читают его как обычный DOM:

```js
function session(t) {
  var node = t.$('#session');
  t.assert(node, 'Терминал ещё ничего не записал — выполни хотя бы одну команду.');
  return JSON.parse(node.textContent);
}

check('git-init', 'Репозиторий создан', function (t) {
  t.assert(session(t).git.initialized, 'Первая команда в новом проекте — git init.');
  return 'Репозиторий инициализирован';
});
```

Эталонное решение такого задания — это `files/solution/index.html` с готовым JSON-состоянием завершённой сессии; стартовое — с пустым. Тогда обычные тесты работают и для терминальных заданий.

Блок `paste` — шаг «сделай у себя»: ученик выполняет команду в своей настоящей консоли и вставляет вывод. В `pattern` пишите регулярку **без обратных слэшей** (`[0-9]` вместо `\d`) — так JSON остаётся читаемым.

Новые команды симулятора добавляются в `src/core/terminal/shell.ts`. Правило то же, что и для проверок: ошибка должна учить. Сначала настоящий вывод git, затем строка с объяснением по-русски.

## Новый промпт в архив

Создайте файл в `content/prompts/`. Имя файла задаёт порядок в списке, поэтому начинайте с номера: `10-my-prompt.md`.

```markdown
---
title: Короткое название в повелительном наклонении
summary: Одно предложение о том, когда этот запрос пригодится.
tags: отладка, вёрстка
source: откуда взят, если промпт не ваш
---
Текст запроса. Места, куда человек подставляет своё, пишите заглавными:
ВСТАВЬ СЮДА КОД.
```

Что делает промпт хорошим:

- **Роль и контекст в первой строке.** «Я новичок, учебный проект на чистом HTML и CSS».
- **Явный формат ответа.** Без него модель вернёт стену текста или урезанный файл.
- **Запрет на лишнее.** «Не улучшай то, о чём я не просил», «никаких библиотек».
- **Объяснение вперёд решения.** Ученику нужен разбор, а не готовый файл, который он не понимает.

Поле `source` обязательно, если промпт взят у другого автора: чужой текст в репозитории под CC BY-SA требует указания авторства и разрешения автора.

## Задания с заказчиком

Задание получает поле `client` с id папки из `content/clients/`. Критерии приёмки в `client.json` ссылаются на `id` проверок из `check.js`; критерии из блока `revision` включаются после указанного числа попыток, а сама правка приходит новой репликой в диалог.

## Перед пул-реквестом

```bash
npm run typecheck && npm test && npm run build
```

Прогоните задание руками в браузере: проверки, использующие геометрию и стили, вне браузера не выполняются, и только ручной прогон покажет, что фидбек понятен человеку.
